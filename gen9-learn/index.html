Tracing Gen9

Everything about Gen9, from nothing. You'll create one user and follow it from sign-up to deletion. At every step you watch it happen: in Chrome's DevTools, in Valkey, in the Postgres databases and ClickHouse, in the logs and in the code that did it. The core path takes about four hours; stop after any part.

  1. Predict, then lookMost steps ask what you expect before you check. Guess first: it's what makes it stick.
  2. Do one thing, notice a fewEach step is one action and the handful of things worth seeing. The map shows where to look.
  3. Go deeper, or don'tSteps marked Deeper trace the rest of what that part touches. Skip them the first time through: the core path never needs them.
  4. Check yourself, look it upEach part ends with questions; come back to Review later tomorrow and next week. The Reference at the end names every service, workflow, route, table, setting and command, each linked to the step that shows it.

What Gen9 is, and for whom

Gen9 is an AI agent you run yourself. People talk to it in a web app or a terminal. It answers with the sources it used, remembers what they ask it to, searches the web and their past chats, runs commands and keeps files in a sandbox of the chat's own, uses the tools of MCP servers they connect, and carries out tasks on a schedule. Other programs can use it too: as an MCP server, an A2A agent, or over AG-UI.

All of it runs on your machine as eight Docker Compose stacks, except the models themselves. Gen9 reaches those through one router, which holds the providers' keys.

What it must do well, and its limits

Five qualities decide most of how Gen9 is built. When two designs would both work, the one that keeps these wins.

QualityWhat it means hereTraced in
A person's data stays theirsThe browser never holds a token. Each service holds only the secrets it uses. Deleting a chat or an account erases it from every store. What outlives an account (the audit record) names no oneParts 1, 9, 10
Work isn't lostAn answer keeps going when the tab closes, the worker dies or the stack restarts. A task runs with nobody signed in. A question the agent asks waits as long as it takesParts 2, 3
Spend is boundedA turn has a step limit. A person has a budget for the month, and the worker's key has one for everyone each day. The router refuses a call over a budget before any provider sees itPart 10

What it is held to, and what it leaves to whoever runs it:

  • Self-hosted, on one Docker host. Every port is published on 127.0.0.1 only. To serve people on a network, put TLS reverse proxies in front of gen9-ui and Keycloak (gen9-ui/README.md, gen9-keycloak/README.md), and give Keycloak and gen9-agent a real SMTP server in place of Mailpit.
  • Models from providers you choose, through the router only. gen9-agent asks for aliases (chat, embed, web…) and never holds a provider key. Whatever it sends a model reaches that provider.
  • The law it is written against: the GDPR's right to erasure (a person's data goes from every store, backups within the operator's rotation), and the EU AI Act's transparency rules, which apply from 2 August 2026 (docs/ai-act.md: what Gen9 does, and what is left to its operator).
  • How it is written: every Python service is async from the ground up, each stack is its own Compose project, and every image is pinned by digest (AGENTS.md).

The cast

The names you'll meet on every page. Knowing them before you start makes the rest easier to follow. First the ones about who someone is:

BFF
Backend-for-Frontend. The browser never holds a token; gen9-ui keeps them server-side and gives the browser only an opaque cookie.
sub
The user's id in Keycloak. Every store keys the user's data by it.
sid
The id of one Keycloak login session. Back-channel logout names it.
aud / azp
Who a token is for (gen9-agent) and which client asked for it (gen9-ui or gen9-cli). The agent checks both.
auth_time
When the user last really signed in. A token refresh doesn't change it; deleting an account checks it.
PKCE, state, nonce
Three one-time values that tie a sign-in's start to its end: stolen codes, forged callbacks and replayed tokens all fail.
kc_action
A Keycloak "account action" (add an authenticator, change the password…) that the app starts with a normal sign-in round trip.
back-channel logout
Keycloak calling gen9-ui directly, server to server, when a session ends anywhere, so gen9-ui drops its copy.
step-up
Asking for a fresh sign-in before a sensitive action when the last real one is too old. gen9-ui asks first; the agent refuses on its own too.
device flow
How the terminal signs in: it shows a code, you confirm it in any browser.

Then the ones about what the agent does:

chat, thread
One conversation. The web app says chat, the API says thread; its id keys the chat's history, trace, files and sandbox.
run
The agent's answer to one message: recorded by the API, executed by a worker, told to whoever follows it as a numbered log of events. A chat has at most one run going.
workflow, Activity
Temporal's units. A workflow is code whose progress survives crashes; an Activity is one step of it that touches the world (a model call, a database write), retried until it succeeds.
Signal, Update
Temporal's messages to a running workflow. A Signal is sent and not answered, as a person's answer reaches a run that waits for it (answered); an Update waits for the workflow's reply, which may be a refusal, as a command asks for its chat's sandbox (acquire).
Schedule
Temporal starting a workflow at set times: each scheduled task has one, and so do Gen9's own chores (the sweep, the syncs).
task
Four things share the word, and each is a run in a chat: a scheduled task starts one at set times; a background task is one the agent starts in a chat of its own while it carries on; an MCP task and an A2A task are what those protocols call one that another program started.
checkpoint, store
LangGraph's saved state. Checkpoints hold a chat's history; the store holds what crosses chats, such as a person's memory.
alias
A model's name at the router: chat, embed, web. gen9-agent asks by alias; the router picks the model and holds its key.
virtual key
A key the router issues, with its own budget and the aliases it may call. The worker's and the API's are different keys.
tool, subagent
What the agent can do besides writing: search, read a file, run a command. A subagent is a helper it hands part of a task to, with its own instructions and a fresh context.
skill, plugin
A skill is a folder of instructions (SKILL.md) the agent reads when a task matches it. A plugin, from a git marketplace, brings skills and MCP servers; an admin decides who gets it.
connector
An MCP server a person added. Its tools join that person's runs, and nobody else's.
environment
A chat's sandbox: a container of its own where the agent's commands run, with a closed network.
trace, observation
Langfuse's record of a run, one observation a step, tagged with the person's sub and the chat's id.
sealed
Encrypted with Gen9's key ring (GEN9_SECRET_KEYS) and bound to its owner, so a copied value doesn't open on another row. Connector tokens and environment secrets are sealed.
Part 0, 10 minutes

Your observation kit

Set up once. Everything else in this guide uses these.

  1. Chrome DevTools

    Open Chrome with DevTools (⌥⌘I), Network tab, and set it up once:

    • Preserve log on. Sign-in hops across two sites (the app on :14000, Keycloak on :15000); without it each redirect wipes the list.
    • Filter to Doc and Fetch/XHR. Ignore ?_rsc= requests: that's Next.js prefetching pages, not your flow.
    • Right-click a column header and turn on Set cookies: it counts the cookies each response sets. Click a request, Cookies tab, to see them with their attributes; the Application tab shows what the browser keeps.
    • For passkeys later: More tools, WebAuthn lets you watch (or emulate) the authenticator.

  2. Terminal: check everything answers

    From the repo root. These are the commands the rest of the guide uses; each works on its own.

    make ps
    docker exec gen9-postgres-postgres-1 psql -U postgres -d gen9_agent -c "\dt public.*"
    docker exec gen9-keycloak-postgres-1 psql -U keycloak -d keycloak -c "select count(*) as users from user_entity"
    docker exec gen9-langfuse-clickhouse-1 clickhouse-client -q "select type, count() from events_core group by type"
    docker exec gen9-ui-valkey-1 sh -c 'REDISCLI_AUTH="$VALKEY_PASSWORD" valkey-cli --scan --pattern "gen9:*"'
    Why no passwords here?

    docker exec runs inside each container, where Postgres trusts local connections and Valkey's password is already in the environment. Nothing is printed that you'd have to hide.

  3. DBeaver: four connections

    All on host 127.0.0.1. Passwords come from each stack's .env; the command after the table prints them in your terminal.

  4. Valkey: a window into the web sessions

    Install Valkey Admin (the Valkey project's own app, Apache 2.0, a .dmg for macOS). Add Connection: Endpoint type Node (Discovery is for clusters and fails with "Failed to discover cluster"), host 127.0.0.1, port 14002 (not 6379, the port inside the container), username empty, the password below, database 0, TLS off (it listens only on your machine).

    grep '^VALKEY_PASSWORD=' gen9-ui/.env

    You'll see keys, their type and time to live, never readable sessions: each value is encrypted with gen9-ui's key. To see what's inside one, this repo has a read-only tool that decrypts it inside gen9-ui's container and prints the fields and token claims, never a token:

    gen9-learn/tools/peek-session.sh ada@gen9.test

  5. Logs

    Docker Desktop's Containers view shows each container's log. In the terminal, follow one stack:

    make logs STACKS=ui FOLLOW=1
    follows; Ctrl-C to stop

    Four containers matter most: gen9-ui-prod-1 (sign-in errors, back-channel logout), gen9-agent-api-1 (every API call with its status), gen9-keycloak-keycloak-1 (startup, realm import) and gen9-keycloak-configure-1 (what it set on the realm at the last start).

    And Keycloak's own audit trail, the most useful single query in this guide:

  2. Submit the form

    Email trace@gen9.test, any first and last name. There's no password field yet.

    Predict: the user now exists in Keycloak. What's missing before it can sign in?

    Two required actions: VERIFY_EMAIL and UPDATE_PASSWORD. Keycloak holds the user back until both are done.

    In the Keycloak DB
    docker exec gen9-keycloak-postgres-1 psql -U keycloak -d keycloak -c "select u.email, u.email_verified, u.enabled, a.required_action from user_entity u left join user_required_action a on a.user_id = u.id where u.email = 'trace@gen9.test'"
    verifiedemail_verified f, enabled t, required actions UPDATE_PASSWORD, VERIFY_EMAIL events so far: REGISTER SEND_VERIFY_EMAIL
    In Mailpit

    localhost:15002: "Verify your email for Gen9", Gen9-styled. No mail ever leaves your machine; Keycloak's SMTP points at Mailpit. It asks for a user and password first: gen9, and this (your own, printed to your terminal):

    sed -n 's/^MAILPIT_UI_PASSWORD=//p' gen9-keycloak/.env
    verifiedwithout it, Mailpit's API answers 401
    Why a mail catcher has a password

    Mailpit holds every email Gen9 and Keycloak send, password-reset links included, and every container on Keycloak's network can reach it. Open, one compromised service could read a reset link and take over any account (docs/auth-architecture.md, decision 12). Sending stays open, so Keycloak and the agent's worker still deliver to it.

Using it

Ask a question, reload (once in the middle of an answer), let it ask before acting, answer its question, see what it remembers and find an earlier chat, then let the access token expire. Covers chat, runs and their workers, streaming, approvals and questions mid-task, memory and past chats, tracing, token checking and the silent refresh.

Only new realms (first start after a wipe of Keycloak). For existing ones, the change belongs in configure.sh, which runs after every start.

Why can't gen9-ui connect to Postgres even with the right password?

Show answer

It isn't on the gen9-postgres network; only the agent is. Each stack joins its own network and those of the stacks it calls.

Someone takes over the API's container. Which keys can't they read there?

Show answer

Langfuse's, the email server's and the sandbox's: the API never uses them, so Compose leaves them empty or out. Its router key can only embed and rerank, and its database role can read and write rows but not alter, drop or create anything. The worker, which runs the agent, holds them all.

The public one (temporal:7233, :18001) serves gen9-agent and the web UI, and takes Keycloak access tokens with Temporal permissions. The internal one (temporal:7236) serves the stack's own tools, the cli among them, over TLS with the internode certificate.

Workflows, Activities and Schedules

Everything gen9-agent's worker runs on Temporal, in namespace gen9. Workflows hold ids only; what people wrote stays in gen9-postgres, and every payload is encrypted with TEMPORAL_PAYLOAD_KEYS (docs/temporal.md). Agent turns go on queue gen9-agent, the rest on gen9-system; a person's chat goes before their scheduled work (priority 1, background 3, sweeps 5).
